== Running on your group's cluster ==
  cluster = a set of shared computers run by your group or a computing center. You hand your calculation to the job scheduler
  (PBS or Slurm; software that manages the queue), and each calculation handed over is called a 'job'.
  The current submit.sh is for this PC. To use a cluster, first do these two things.
  a. Add a profile with kind = "pbs" or "slurm" to the ADIT settings file, which is at
       /home/<user>/.config/adit/cluster.toml
     The shortest form is below. Append it to the end of the file and replace <...> with your values (from # to the end of a line
     is a comment and may be removed). Queue names and module names (the names that make a program available on the cluster) differ
     between clusters, so ask the administrator or a senior member of your group.
       [profiles.remote]
       kind = "pbs"                                # "slurm" for a Slurm cluster
       header_extra = ["#PBS -q <queue>"]           # Slurm: ["#SBATCH --partition=<partition>"]
       [profiles.remote.code_modules]
       dftbplus = ["<module name>"]                 # module that makes the program available (module avail on the cluster lists them)
     Other items (submit command, environment variables, run commands, ...) are in ADIT's docs/SETTINGS.md (settings), section 'Running on a cluster'.
  b. Switch the profile in ADIT to it and generate again. submit.sh becomes a job script for qsub (PBS) / sbatch (Slurm),
     and this README.txt then shows the submit and status commands for that cluster.
  The steps after that are as follows (replace <...> with your own values).
  1. Copy this whole directory to the cluster (in a terminal on your PC; scp / rsync = commands that copy files over the network)
     Replace <path to this calculation directory> with its current location on your PC.
       scp -r '<path to this calculation directory>' <user>@<cluster host name>:<work directory on the cluster>/
     or
       rsync -av '<path to this calculation directory>' <user>@<cluster host name>:<work directory on the cluster>/
  2. Log in to the cluster and move into the copied directory (ssh = the command that logs in to another computer)
       ssh <user>@<cluster host name>
       cd <work directory on the cluster>/disp-004
  3. Submit the job. If a job number is printed, it was accepted
       qsub submit.sh     (PBS)   /   sbatch submit.sh   (Slurm)
  4. Check the status ($USER expands to your user name). When the job disappears from the list, it has finished
       qstat -u $USER     (PBS)   /   squeue -u $USER    (Slurm)
  5. When it has finished, copy the results back (in a terminal on your PC)
       scp -r <user>@<cluster host name>:<work directory on the cluster>/disp-004 <local folder>/
     or
       rsync -av <user>@<cluster host name>:<work directory on the cluster>/disp-004 <local folder>/

== What the documents suggest when a run fails ==
  For each message ADIT finds in the output (the 'possible causes of failure' line of the analysis summary), this quotes what the code's own documents suggest.
  These are not ADIT's recommendations; the numbers and steps are as in the sources, and whether they suit your system is your call.
  - 'SCC is NOT converged, maximal SCC iterations exceeded': the DFTB+ recipes explain that convergence is judged by SccTolerance (default 1e-5 electrons) with MaxSccIterations (default 100) as the limit, and that on reaching it the code 'calculates the total energy using the charges obtained so far and stops with an appropriate warning message'. Source: https://dftbplus-recipes.readthedocs.io/en/latest/basics/firstcalc.html
  - same: the DFTB+ manual says that for non-static runs (Driver not empty) ConvergentSccOnly can override the stop (MaxSCCIterations entry). Source: https://github.com/dftbplus/dftbplus/blob/main/doc/dftb+/manual/dftbp.tex
  - '!!! Geometry did NOT converge!': in the manual MaxSteps is the number of steps after which the optimization stops unless converged; -1 means practically unlimited. Source: https://github.com/dftbplus/dftbplus/blob/main/doc/dftb+/manual/dftbp.tex
  - 'WARNING! -> Current stacksize not set to unlimited': DFTB+'s own warning, advising ulimit -s unlimited (the cluster submit.sh already has it). Source: the DFTB+ output itself
  - 'DUE TO TIME LIMIT' (Slurm) / '=>> PBS: job killed: walltime … exceeded limit …' (PBS): the walltime limit was hit. Sources: Slurm slurmstepd https://github.com/SchedMD/slurm/blob/master/src/slurmd/slurmstepd/req.c, OpenPBS pbs_mom https://github.com/openpbs/openpbs/blob/master/src/resmom/mom_main.c
  - 'oom_kill event … OOM Killed' (Slurm) / '=>> PBS: job killed: mem …' (PBS) / 'Out of memory: Killed process' (Linux) / a 'Killed' line: killed for lack of memory. Sources: Slurm https://github.com/SchedMD/slurm/blob/master/src/plugins/task/cgroup/task_cgroup_memory.c, Linux https://github.com/torvalds/linux/blob/master/mm/oom_kill.c
  - 'MPI_ABORT was invoked on rank …' (Open MPI) / 'application called MPI_Abort', 'BAD TERMINATION OF ONE OF YOUR APPLICATION PROCESSES' (MPICH): an MPI process aborted; the reason is in the code's lines before it. Sources: Open MPI help-mpi-api.txt (shipped with Open MPI), MPICH https://github.com/pmodels/mpich/blob/main/src/pm/hydra/mpiexec/pmiserv_cb.c
